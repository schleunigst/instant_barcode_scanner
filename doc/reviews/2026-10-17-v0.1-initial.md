## 1. Verdict

**Request changes — do not device-test until R1–R3 are fixed.** The
mechanism is a credible lift of the p5 skeleton and the Dart/pigeon
scaffolding is clean, but the port added two things p5 never had —
*overlapping `driveTo` commands with per-call result futures*, and *a
per-controller `dispose()`* — and neither was reconciled with the fact that
`openDevice`/`configureSession` are asynchronous. As written, `close()` /
`dispose()` can lie about the camera being closed (R1/R2/R4), and a second
controller after `dispose()` can never scan again (R3). The package's central
promise ("truthful close") is exactly what breaks. The claimed verification
(analyze + 13 Dart tests + debug APK) never compiles the one Kotlin test,
never runs instrumentation, and never exercises R8, so none of these paths
are protected.

## 2. Strengths

- Mechanism/policy split is real and matches §4: native is device lifecycle
  only; `ScannerPolicy` is pure, testable Dart (`policy.dart`).
- `settle()`/`emitChanged()` centralize state publication and dedupe
  (CameraMechanism.kt:179-204); every convergence path terminates in one
  settle.
- rawBytes pass-through is genuinely untouched end-to-end (`mapBarcode`
  CameraMechanism.kt:492-499, `_resultFromPigeon` platform.dart:100-106);
  `text` is explicitly best-effort in docs and code.
- Thread separation is mostly right: camera ops on one HandlerThread, ML Kit
  on `ibs-analysis`, `streaming` volatile and `analysisBusy` atomic with the
  p4/p5 busy gate.
- `consumer-rules.pro` matches the proven p4 rules verbatim.
- Texture/entry cleanup is idempotent and null-safe on the plugin
  (`releaseTexture` plugin.kt:118-129); `onDetachedFromEngine` disposes the
  mechanism before releasing the texture.
- Good doc hygiene in types.dart/README on the raw-bytes contract and the
  limitations section.

## 3. Code findings (R1–R12)

### R1 — Blocker — Overlapping `driveTo` corrupts convergence: double `openCamera`, double `createCaptureSession`, and a `close()` that leaves the camera open

**Affected:** `CameraMechanism.kt:90-113` (driveTo), `:211-272` (converge),
`:274-339` (openDevice), `:350-389` (configureSession).

`converge` decides what to do purely from the *current fields*; it has no
"open in flight" or "configure in flight" flag. A second `driveTo` posted
while the first's async open is pending runs `converge` again and sees
`device == null` (line 220) → calls `openCamera` a second time (line 221).
Analogously, two chains can both observe `session == null` (line 242) and
call `createCaptureSession` twice (line 243). Consequences:

- The second `openCamera` will typically fail
  (`CAMERA_IN_USE`/`MAX_CAMERAS_IN_USE`), whose `done(false)` path
  `settle()`s `(CLOSED, open_failed)` for **all** pending futures
  (lines 222-231) while the first chain continues and silently
  configures/streams — so `scan()` throws `ScannerException(closed/open_failed)`
  and then the UI receives a `live` state event with no scan attached.
- `driveTo(closed)` while open is in flight goes through `!target.device`
  (lines 212-218), sees `device == null`, settles `CLOSED` — and then the
  open completes and the parked/live chain finishes. **Dart was told the
  camera is closed while the device is actually opening and left open.**
  This is precisely the §6 race rule "stop-while-opening (retarget)"
  (design doc:149-151) that this port drops.
- p5 had the same structural shape but a single serial external driver
  (MainActivity.kt:347-406); it never needed re-entry protection. This
  package explicitly advertises retargeting and its own controller issues
  overlapping commands (example buttons at `example/lib/main.dart:135-147`;
  `scan()` racing `warmUp()`).

**Fix:** add an explicit state (`openInFlight`, `configureInFlight`) plus a
single `pendingTarget`; when a step completes, re-run convergence for the
latest target instead of starting a second async op. Never settle `CLOSED`
while an open is in flight — either cancel/close after it completes or defer
the settle.

### R2 — Blocker — `dispose()` races an in-flight open and can leave the camera device open forever

**Affected:** `CameraMechanism.kt:115-152` (dispose), `:302-339` (openDevice
callbacks), `:154-163` (cameraHandlerFor).

`dispose()` posts teardown to the camera thread, then `quitSafely()`s the
thread. But `converge`, `onOpened`, `onDisconnected`/`onError` never check
`disposed` (grep: no `disposed` reference in converge/openDevice). If the
open callback is delivered before the queued teardown, `onOpened` sets
`device` and re-enters `converge`, which can configure a session and even
`startRepeating` after the teardown already ran — on a `Surface` that
`releaseTexture()` is concurrently releasing. If the callback is dropped
(posted after `quitSafely`), the HAL-level device is open with no owner and
nothing will ever `close()` it. Either way the camera-in-use indicator can
stay on after `dispose()`. Also, `disposed` is a plain `var` written on one
thread and read on another, and `cameraHandlerFor()` can spin up a *new*
HandlerThread if called after dispose nulled `cameraHandler` (`:154-163`) —
a second camera thread with unsynchronized access to all fields.

**Fix:** make `disposed` `@Volatile` (or keep all mutation on the camera
thread), check it in `onOpened/onError/onDisconnected` and at the top of
`converge`, and in dispose record `closingAfterOpen = true` so a late
`onOpened` immediately closes the device.

### R3 — Blocker — `dispose()` is terminal at plugin scope: every controller created afterwards is permanently dead

**Affected:** `InstantBarcodeScannerPlugin.kt:92-106` and `:108-116`;
`platform.dart:12-15`; README:47-55; `example/lib/main.dart:33,47-51`.

`plugin.dispose()` nulls `mechanism` but leaves `registry`, the pigeon
handlers, and the plugin attached. Dart's platform is a never-invalidated
static singleton (`platform.dart:12-15`), so a new controller gets the same
platform, and:

- `getTextureId()` still works (`registry` non-null, `:69-83`), creating a
  fresh texture;
- `driveTo(...)` hits `mechanism == null` and returns
  `PlatformSnapshot(FAILED, "detached", "plugin is not attached to a Flutter engine")`
  (`:92-98`) — a false message, and Dart silently ignores it (R6), so
  `warmUp()` "succeeds" with no camera and `scan()` times out.

The README and the example both teach create-dispose-per-screen
(`README.md:34-55`, `example/lib/main.dart:33/47-51`), so navigating away and
back to the scanner screen bricks scanning until the engine is recreated
(app restart). Hot restart does not recreate the plugin either.

**Fix:** treat `plugin.dispose()` as reset, not teardown: keep/recreate
`CameraMechanism` lazily on the next `driveTo`/`getTextureId`, or don't null
it and add an explicit shutdown only in `onDetachedFromEngine`. Also clear
the platform singleton (or document a session-lifetime controller).

### R4 — Major — `await scanner.dispose()` does not mean the camera is closed; pending scans are orphaned

**Affected:** `Messages.g.kt:545-560` (generated `dispose` is non-suspend,
replies immediately), `InstantBarcodeScannerPlugin.kt:108-116`,
`controller.dart:157-168` and `:96-118`.

Because the pigeon `dispose()` is `void` (not `@async`), the plugin returns
as soon as it has *posted* teardown; Dart's future completes while the
camera thread is still closing. This directly contradicts §6 "Futures
complete on platform-confirmed state events" (design doc:146-147) and the
README's truthful-close claim. Related: `controller.dispose()` nulls
`_pendingScan` (`:164`) without completing the completer, so a `scan()`
awaiting barcodes is left hanging until its timeout (`:109-114`) — 10 s by
default, arbitrarily long if the caller passed a long timeout. Late
barcodes are then dropped with no observable path (no `scans` stream, see
D3).

**Fix:** make `dispose` an `@async` host method that completes after the
camera thread has closed device/session/reader, or add a `closed`
confirmation snapshot before replying; in Dart, complete `_pendingScan` with
an error in `dispose()`.

### R5 — Major — NFC handoff does not honor design §9: no camera-availability wait, no re-drive on `endNfcHandoff`

**Affected:** `controller.dart:139-154`; no `registerAvailabilityCallback`
anywhere in `android/src/` or `lib/` (verified by grep); design §9
(INSTANT_BARCODE_SCANNER.md:198-213).

§9 requires `beginNfcHandoff()` to "wait for camera availability
(`onCameraAvailable`) + settle delay before opening the NFC reader" —
measured ~0.19 s after `close()` returns. The implementation resolves when
`dev.close()` returns (`CameraMechanism.kt:341-348`), so a host that does
`await beginNfcHandoff(); nfc.enableReaderMode(...)` hits exactly the race
the package exists to eliminate ("the proof of the whole package thesis").
`endNfcHandoff()` only clears the flag and touches the idle timer
(`:148-154`): with state `closed`, `idleDelay(closed)` is null, so nothing
is re-driven — the previous parked target is not resumed, contrary to §9.3.
`beginNfcHandoff` also sets `_handoff = true` before the await (`:141`), so
if `driveTo` throws, the scanner permanently rejects `scan()` until
`endNfcHandoff()` is called.

**Fix:** register a `CameraManager.AvailabilityCallback` in the plugin and
have `driveTo(closed)` (or a dedicated handoff channel) complete only when
the camera reports available (+ optional settle knob, §14); make
`endNfcHandoff()` async and drive back to the captured pre-handoff target.

### R6 — Major — The controller ignores every `driveTo` snapshot except the scan's; `park()` can silently cancel the close timer forever

**Affected:** `controller.dart:73-77` (warmUp), `:121-126` (park), `:129-134`
(close), `:139-145` (beginNfcHandoff), `:200-213` (`_touchIdle`);
`CameraMechanism.kt:194-204` (dedupe).

`platform.dart:29-32` tells callers "the future may complete with a state
other than target … callers must check the result" — the controller is the
caller and never checks. Concretely: `await scanner.close()` can return while
the native state is `live/parked` (R1 retarget), and `await scanner.warmUp()`
completes "successfully" when open failed (native returns
`CLOSED/open_failed`, silently discarded). Worse, `park()` while already
`parked` cancels `_idleTimer` (`:123-124`), the native settle is deduped by
`emitChanged` (state and errorCode unchanged, `CameraMechanism.kt:194-204`),
no Dart event fires, and `park()` never re-arms the timer — the
parked→closed policy is dead and the device stays open indefinitely.
`ScannerException`'s doc says it is "thrown when the mechanism could not
reach a requested state" (types.dart:91-92) but only `_runScan` ever throws
it.

**Fix:** check the returned snapshot in all drive methods (throw
`ScannerException`/complete with it), and always re-evaluate the idle timer
from the returned status (or stop deduping same-state events that carry a
completed command).

### R7 — Major — No analysis generation/epoch: a stale frame can satisfy the next scan; a visible barcode resets idle forever

**Affected:** `CameraMechanism.kt:450-483` (listener; `streaming` gate at
`:468`), `controller.dart:189-198` (`_handleBarcodes` → `_touchIdle`).

Two related behaviors:

1. ML Kit work from the last live frame can complete after `stopRepeating`
   and after a new `scan()` has started; `streaming` is true again by then,
   so `onBarcodes` fires (`:468`) and `_handleBarcodes` completes the *new*
   scan with the previous scene's barcode. There is no session/frame epoch.
   The p5/p4 references only logged barcodes, so this hazard is new.
2. `_handleBarcodes` calls `_touchIdle()` on **every** batch, even with no
   `_pendingScan` (`:197`). While a barcode remains in view, the native
   emits ~every analysis cycle, so `live` never reaches `parkAfter` — the
   camera stays lit at ~12.7 %/h (design doc:116) as long as a symbol is
   visible.

**Fix:** tag frames with a monotonically increasing capture-generation and
drop results whose generation predates the current live epoch; only reset
idle on delivered scan results (or on explicit activity), not on every
decoded frame.

### R8 — Major — Failure attribution is wrong and there is no recovery path

**Affected:** `CameraMechanism.kt:224-230`, `:259-262`, `:311-331`,
`:401-418`.

A mid-session disconnect (call, other app, backgrounding) arrives in the
device callback whose `done(false)` closure belongs to the original
`openDevice` call, so `converge` settles
`(CLOSED, "open_failed", "camera device failed to open")` (`:224-230`) — the
message describes an open failure that did not happen. If a `driveTo` is
pending at that moment it also gets that wrong snapshot. `startRepeating`
swallows exceptions (`:415-417`) and then `converge` settles
`currentState()` — i.e. `PARKED` with **null** error (`:259-262`), so
`scan()` throws `ScannerException(parked)` with no
`errorCode`/`errorMessage`. §5/§6 call for disconnect → recovery (design
doc:128-129, general) and §14 budgets it; nothing here re-drives or even
labels the failure.

**Fix:** distinguish `open_failed`, `disconnected`, `configure_failed`,
`repeating_failed` codes; have `onDisconnected` emit its own snapshot (and
optionally re-drive the last confirmed target per §6).

### R9 — Major — The Kotlin unit test does not compile; the native test suite has never run

**Affected:** `android/src/test/kotlin/.../InstantBarcodeScannerPluginTest.kt:18-26`;
`android/build.gradle.kts:52-66,82-83`.

The test calls `plugin.onMethodCall(call, mockResult)` and mocks
`getPlatformVersion`, but `InstantBarcodeScannerPlugin` implements
`FlutterPlugin, ScannerHostApi` and has no `onMethodCall`/`getPlatformVersion`
(grep confirms the only occurrence of `onMethodCall` in the repo is this
test). It cannot compile. Evidence it was never compiled: no
`InstantBarcodeScannerPluginTest.class` exists anywhere under
`example/build/` (only main classes were built), so the "debug APK builds"
claim bypasses it. Running `./gradlew test` on the example would fail at
compile time. The `testOptions`/`kotlin-test`/`mockito-core:5.0.0` block is
therefore dead weight, and there are zero native tests for convergence,
retargeting, or dispose.

**Fix:** delete or rewrite the template test against the real
`ScannerHostApi`/`CameraMechanism` seams, and make it part of the
verification story (plus the §13 instrumentation tests).

### R10 — Minor — Dart async/dispose edges: disposed notifier write, cached texture failure, stuck handoff flag

**Affected:** `controller.dart:157-179` and `:236-240`.

- `dispose()` disposes `_textureId` (`:167`), but `_ensureTexture()`'s
  pending `.then` still writes `_textureId.value = id` (`:175-178`). Any
  `dispose()` racing the first `warmUp()`/`scan()` triggers a
  `ChangeNotifier` "used after being disposed" assertion in debug (silently
  no-ops in release).
- `_textureFuture ??=` caches a **failed** future forever; a transient
  `getTextureId` failure permanently poisons `warmUp`/`scan` with no retry.
- As noted in R5, a throw during `beginNfcHandoff` leaves `_handoff = true`
  permanently.
- After `dispose()`, the public `state` getter reads a disposed
  `ValueNotifier` and throws in debug.

### R11 — Minor — `scanner` (ML Kit client) is created on the analysis thread and closed on the camera thread without synchronization

**Affected:** `CameraMechanism.kt:463` (`scannerInstance()` on analysis
thread), `:485-490`, `:131-140` (`scanner?.close()` in dispose on camera
thread).

There is no happens-before between the analysis-thread write and the
camera-thread read; a stale read can skip `close()` (leak), and closing
while a task is in flight is unguarded. In practice HandlerThread queue
synchronization makes the leak unlikely, but the field is simply not safe as
written. Make `scanner` eager (created once on the camera thread in the
constructor) and closed there.

### R12 — Minor — `getTextureId()` after dispose can mint an orphan texture

**Affected:** `InstantBarcodeScannerPlugin.kt:69-83`, `:108-129`.

`dispose()` never nulls `registry`, and `releaseTexture()` only runs as the
dispose callback. A `getTextureId` that lands after the release (e.g., a
racing `_ensureTexture`, R10) creates a new `SurfaceTextureEntry` that
nothing will ever release. The same ordering leaves
`InstantBarcodeScannerView` referencing a released texture id. Keep a
`released` flag / re-check `mechanism` before creating.

## 4. Design findings (D1–D10)

### D1 — Major — No app-lifecycle handling at all (contradicts §5/§6)

**Affected:** no `ActivityAware`/lifecycle code in `android/src/` (verified
by grep); design doc:127 ("Any → closed on app background") and :152-153
(pause/resume re-drive).

On Android 9+, a backgrounded app loses camera access; the framework
disconnects the device, which lands in the misattributed path of R8, and on
resume nothing re-drives the last target. For a package whose litmus is a
long-lived cashier session, background/foreground is a first-class
transition. If deliberate deferral, the README should say so; today neither
design nor README matches behavior.

### D2 — Major — Scan does not auto-park; design and README disagree

**Affected:** `controller.dart:84-118`; design doc:122-123 ("live → parked:
immediately after a read burst") and :164 (`scan` … "auto-park");
README:57-58 (park after 15 s).

After a successful scan the controller leaves the scanner `live` until
`parkAfter` (15 s default) — i.e. the indicator stays on and the package
pays 12.7 %/h for up to 15 s after every read, which is the opposite of the
design's "immediately after a read burst". Decide the contract and align
doc/impl; if auto-park is wanted, `scan()` should `driveTo(parked)` on
completion (while keeping a warm session).

### D3 — Major — No `Stream<ScanEvent>` / no way to observe barcodes outside a scan

**Affected:** `lib/` has no stream API (verified); design doc:161.

The §7 API sketch includes `Stream<ScanEvent> get scans`. Its absence
means: barcodes that arrive after `scan()` returns or times out are dropped
forever (R4/R7), repeated scans can never be honored as events, and advanced
flows (continuous monitoring without a pending future) are impossible. The
raw-bytes contract is weakened because the only delivery path is a single
await.

### D4 — Major — `failed` state and failure idling are not implemented; failures can hold the camera open indefinitely

**Affected:** `CameraMechanism.kt:242-257` (configure failure settles state
`OPEN` + `configure_failed`), `policy.dart:24-30` (`idleDelay(open) ==
null`), `types.dart:45-55`.

The public enum documents `failed` "carries last state for recovery" (design
doc:118), but the native mechanism never emits `PlatformState.FAILED` for
real failures (only the plugin's detached path) and `converge` returns
`CLOSED` or `OPEN`. A `configure_failed` leaves the device **open** with no
idle step (`open` has no delay/target), so if the app doesn't explicitly
retry/close, the camera is held open with the indicator on — directly
against "never holds the device while idle" (README:8-9). Add a failure
policy (close, or a retry timer) and/or emit `failed`.

### D5 — Minor — Capability reporting is a constant; policy never consults it

**Affected:** `InstantBarcodeScannerPlugin.kt:85-90`, `platform.dart:74-80`,
`controller.dart:66`; design §11 (doc:254-265).

`supportsPark`/`supportsTrueClose` are hardcoded `true` and no code path
reads them, so the "platform-neutral degradation contract" is currently
decorative — and `supportsTrueClose` is only true on the happy path given
R1/R4. Fine as a forward-looking surface, but be honest in docs, and ideally
derive it (e.g., from a real availability callback).

### D6 — Minor — The documented unbundled ML Kit swap is not actionable for consumers

**Affected:** `README.md:93-98`.

"Replace the dependency in the plugin's `android/build.gradle.kts`" means

## 5. Questions for the author

1. **Repo identity:** does `github.com/instantbarcode` exist and is the repo
   there? The `homepage`/`repository`/`issue_tracker` URLs (pubspec.yaml:7-9)
   could not be verified offline, and §12:287 claims the name was checked
   free.
2. **Dispose semantics (R3):** is per-controller `dispose()` intended to
   permanently kill scanning for the engine? If so, how should hosts
   implement "leave the screen and come back" — one app-lifetime controller
   with `close()`? README/example currently suggest the opposite.

5. **Stale frames (R7):** is completing a new scan with a frame decoded
   before the scan started acceptable, or should there be an epoch?
